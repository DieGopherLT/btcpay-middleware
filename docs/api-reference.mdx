# API Reference

## `BTCPayMiddleware` namespace

```ts
import { BTCPayMiddleware } from '@taloon/btcpay-middleware';

BTCPayMiddleware.configure(config);
BTCPayMiddleware.createInvoice(options);
BTCPayMiddleware.getInvoice(options);
BTCPayMiddleware.invoiceWebhook(options);
BTCPayMiddleware.createPayout(options);
BTCPayMiddleware.getPayout(options);
BTCPayMiddleware.payoutWebhook(options);
```

You can also import each middleware as a named export — both styles are equivalent.

---

## `configure(config)`

```ts
interface BTCPayConfig {
  baseURL: string;            // BTCPay Server URL, e.g. https://btcpay.example.com
  apiKey: string;             // API key for the Greenfield API
  storeId: string;            // Store id
  webhookSecret?: string;     // HMAC secret matching the BTCPay webhook UI
  errorHandling?: 'next' | 'direct';
  onError?: ErrorHandler;
}

BTCPayMiddleware.configure(partial: Partial<BTCPayConfig>): void;
```

- Merges `partial` into the existing config (which is initially read from env vars).
- Required keys (`baseURL`, `apiKey`, `storeId`) are validated lazily, on the first middleware call.
- `errorHandling` is the fallback strategy when neither a per-middleware nor a global `onError` is provided:
  - `'next'` (default) — call `next(error)` so your Express error handler picks it up.
  - `'direct'` — write a JSON error body directly with the appropriate status code.

## `createInvoice(options)`

```ts
interface CreateInvoiceMiddlewareOptions {
  mapRequest: (req: Request, res: Response) => CreateInvoiceRequest;
  transformResponse?: (invoice: BTCPayInvoice) => unknown;
  onError?: ErrorHandler;
}
```

`mapRequest` produces the body sent to `POST /api/v1/stores/{storeId}/invoices`. `amount` and `currency` are required — anything else is optional.

Result is stored on `res.locals.btcpayResponse` (raw `BTCPayInvoice` unless `transformResponse` is provided).

```ts
interface CreateInvoiceRequest {
  amount: number | string;
  currency: string;
  orderId?: string;
  buyerEmail?: string;
  description?: string;
  checkout?: InvoiceCheckoutOptions;
  metadata?: Record<string, unknown>;
}
```

`orderId`, `buyerEmail`, and `description` are flattened into BTCPay's `metadata` field on the wire (`orderId`, `buyerEmail`, `itemDesc` respectively).

## `getInvoice(options)`

```ts
interface GetInvoiceMiddlewareOptions {
  mapRequest: (req: Request, res: Response) => string; // returns invoiceId

  onError?: ErrorHandler;
```

Reads `GET /api/v1/stores/{storeId}/invoices/{invoiceId}` and stores the result on `res.locals.btcpayResponse`.

## `invoiceWebhook(options)`

```ts
interface InvoiceWebhookMiddlewareOptions {
  onCreated?:         (payload: BTCPayWebhookPayload) => void | Promise<void>;
  onReceivedPayment?: (payload: BTCPayWebhookPayload) => void | Promise<void>;
  onProcessing?:      (payload: BTCPayWebhookPayload) => void | Promise<void>;
  onSettled?:         (payload: BTCPayWebhookPayload) => void | Promise<void>;
  onPaymentSettled?:  (payload: BTCPayWebhookPayload) => void | Promise<void>;
  onExpired?:         (payload: BTCPayWebhookPayload) => void | Promise<void>;
  onInvalid?:         (payload: BTCPayWebhookPayload) => void | Promise<void>;
  onError?: ErrorHandler;
}
```

Mount with `express.raw({ type: 'application/json' })`. When `webhookSecret` is configured the `BTCPay-Sig: sha256=<hex>` header is verified against the raw body before dispatch. The middleware always responds `200 OK` on success and stores the parsed payload on `res.locals.btcpayResponse`.

## `createPayout(options)`

```ts
interface CreatePayoutMiddlewareOptions {
  mapRequest: (req: Request, res: Response) => CreatePayoutRequest;
  transformResponse?: (payout: BTCPayPayout) => unknown;
  onError?: ErrorHandler;
}

interface CreatePayoutRequest {
  destination: string;          // wallet address (or BIP21 url)
  amount: string;               // amount in the store's default currency
  payoutMethodId: PayoutMethod; // 'BTC-CHAIN' | 'BTC-LN'
  approved?: boolean;           // defaults to true (auto-approve)
  metadata?: Record<string, unknown>;
}
```

`mapRequest` produces the body sent to `POST /api/v1/stores/{storeId}/payouts`. `destination`, `amount`, and `payoutMethodId` are required.

By default the middleware sets `approved: true`, so the payout is enqueued for the configured **payout processor** (on-chain or Lightning) in a single round-trip. Pass `approved: false` to leave the payout in `AwaitingApproval` for manual review.

> **Pre-requisite**: the store must have a payout processor configured in BTCPay (UI: *Store Settings → Payouts → Configure*). Without one, approved payouts stay in the queue and the transaction is never broadcast. This library does not manage that configuration.

The `metadata` field is a transparent pass-through — useful to stamp internal identifiers (e.g. `referralId`, `userId`) that show up on later webhook events for reconciliation.

Result is stored on `res.locals.btcpayResponse` as a `BTCPayPayout` (or whatever `transformResponse` returns).

## `getPayout(options)`

```ts
interface GetPayoutMiddlewareOptions {
  mapRequest: (req: Request, res: Response) => string; // returns payoutId
  transformResponse?: (payout: BTCPayPayout) => unknown;
  onError?: ErrorHandler;
}
```

Reads `GET /api/v1/stores/{storeId}/payouts/{payoutId}` and stores the result on `res.locals.btcpayResponse`. Inspect `state` (`AwaitingApproval` / `AwaitingPayment` / `InProgress` / `Completed` / `Cancelled`) and `paymentProof` to drive reconciliation.

## `payoutWebhook(options)`

```ts
interface PayoutWebhookMiddlewareOptions {
  onPayoutCreated?:  (payload: BTCPayPayoutWebhookPayload) => void | Promise<void>;
  onPayoutApproved?: (payload: BTCPayPayoutWebhookPayload) => void | Promise<void>;
  onPayoutUpdated?:  (payload: BTCPayPayoutWebhookPayload) => void | Promise<void>;
  onError?: ErrorHandler;
}
```

Mount with `express.raw({ type: 'application/json' })` and signs identically to `invoiceWebhook`. The three events are the only ones BTCPay emits for payouts:

- `PayoutCreated` — fires when a payout is created (server-side or via pull payment claim).
- `PayoutApproved` — fires when a payout is approved (in this lib, typically in the same call as create).
- `PayoutUpdated` — covers every subsequent state transition: `AwaitingPayment → InProgress → Completed` (or `Cancelled`). Inspect `payload.state` and `payload.paymentProof` to decide what to do.

> **Webhook payload shape note**: BTCPay's Greenfield spec does not publish a dedicated schema for payout webhook payloads (unlike `WebhookInvoiceSettledEvent` et al.). This lib types known base fields strictly and allows any additional field via `[key: string]: unknown`. Types will be tightened in a future release once the exact contract is validated against a live instance.

## Types

```ts
enum InvoiceStatus {
  NEW = 'New',
  PROCESSING = 'Processing',
  EXPIRED = 'Expired',
  INVALID = 'Invalid',
  SETTLED = 'Settled',
}

enum WebhookEventType {
  INVOICE_CREATED = 'InvoiceCreated',
  INVOICE_RECEIVED_PAYMENT = 'InvoiceReceivedPayment',
  INVOICE_PROCESSING = 'InvoiceProcessing',
  INVOICE_SETTLED = 'InvoiceSettled',
  INVOICE_PAYMENT_SETTLED = 'InvoicePaymentSettled',
  INVOICE_EXPIRED = 'InvoiceExpired',
  INVOICE_INVALID = 'InvoiceInvalid',
  PAYOUT_CREATED = 'PayoutCreated',
  PAYOUT_APPROVED = 'PayoutApproved',
  PAYOUT_UPDATED = 'PayoutUpdated',
}

enum PayoutState {
  AWAITING_APPROVAL = 'AwaitingApproval',
  AWAITING_PAYMENT = 'AwaitingPayment',
  IN_PROGRESS = 'InProgress',
  COMPLETED = 'Completed',
  CANCELLED = 'Cancelled',
}

enum PayoutMethod {
  BTC_CHAIN = 'BTC-CHAIN',
  BTC_LN = 'BTC-LN',
}

interface BTCPayInvoice {
  id: string;
  storeId: string;
  amount: string;
  currency: string;
  status: InvoiceStatus;
  additionalStatus?: InvoiceAdditionalStatus;
  checkoutLink: string;
  monitoringExpiration: number;
  expirationTime: number;
  createdTime: number;
  metadata?: Record<string, unknown>;
}

interface BTCPayWebhookPayload {
  deliveryId: string;
  webhookId: string;
  originalDeliveryId: string;
  isRedelivery: boolean;
  type: WebhookEventType;
  timestamp: number;
  storeId: string;
  invoiceId: string;
  metadata?: Record<string, unknown>;
}

interface BTCPayPayout {
  id: string;
  revision: number;
  pullPaymentId?: string;
  date: string;
  destination: string;
  originalCurrency: string;
  originalAmount: string;
  payoutCurrency: string;
  payoutAmount?: string | null;
  payoutMethodId: PayoutMethod;
  state: PayoutState;
  paymentProof?: PayoutPaymentProof | null;
  metadata?: Record<string, unknown>;
}

interface BTCPayPayoutWebhookPayload {
  deliveryId: string;
  webhookId: string;
  originalDeliveryId: string;
  isRedelivery: boolean;
  type: WebhookEventType;
  timestamp: number;
  storeId: string;
  payoutId: string;
  payoutState?: PayoutState;
  [key: string]: unknown; // permissive — see "payload shape note" above
}
```

## Errors

All errors inherit from `BTCPayError`:

| Class                          | Code                       | statusCode |
| ------------------------------ | -------------------------- | ---------- |
| `BTCPayApiError`               | `API_ERROR`                | from BTCPay (4xx/5xx) |
| `BTCPayConfigError`            | `CONFIG_ERROR`             | undefined  |
| `BTCPayValidationError`        | `VALIDATION_ERROR`         | undefined  |
| `BTCPayNetworkError`           | `NETWORK_ERROR`            | undefined  |
| `BTCPayWebhookSignatureError` | `WEBHOOK_SIGNATURE_ERROR` | 401        |

See [error-handling.mdx](./error-handling.mdx) for examples.

## Lower-level utilities

```ts
import {
  BTCPayClient,
  computeSignature,
  verifyWebhookSignature,
  WEBHOOK_SIGNATURE_HEADER,
} from '@taloon/btcpay-middleware';
```

- `BTCPayClient` — direct HTTP client. Useful in scripts and tests.
- `computeSignature(rawBody, secret)` — returns the hex SHA-256 HMAC.
- `verifyWebhookSignature(rawBody, header, secret)` — throws `BTCPayWebhookSignatureError` on mismatch.
- `WEBHOOK_SIGNATURE_HEADER` — the lowercase header name used by `req.headers`.
